# Current State

Дата фиксации: 2026-05-13.

Проект: frontend интернет-магазина цветов Myata Flowers.

Цель документа: зафиксировать текущее поведение Vite SPA перед редизайном, SEO-работами,
решением по CMS и возможным Next.js POC.

## Короткий вывод

Текущий сайт рабочий: показывает каталог, открывает карточки букетов, принимает заявки,
ведет пользователя в мессенджеры и дает владельцу ручную админку для каталога.

Главное ограничение: это клиентский Vite SPA, поэтому SEO, посадочные страницы, metadata
по категориям/букетам и контентная структура ограничены. Переход на Next.js имеет смысл
рассматривать после фиксации текущего поведения и маленького POC, а не как немедленную
полную перепись.

## Локальный запуск

Основная команда разработки:

```bash
npm run mob
```

Причина: backend CORS может разрешать сетевой адрес компьютера, но не `localhost`.
Актуальный `Network`-адрес нужно брать из вывода Vite.

Дополнительные команды:

```bash
npm run dev
npm run check
npm run build
```

## Деплой

Текущий frontend деплоится как статика.

```text
source: /srv/frontend-myata
build:  /srv/frontend-myata/dist
prod:   /var/www/myata-flowers.ru
domain: myata-flowers.ru, www.myata-flowers.ru
type:   Vite SPA
```

Типовой порядок:

```bash
cd /srv/frontend-myata
git pull
npm ci
npm run build
rsync -av dist/ /var/www/myata-flowers.ru/
```

Перед изменением деплоя важно сохранить этот простой путь отката: собрать старую SPA
и снова положить `dist` в `/var/www/myata-flowers.ru`.

## Модалки букетов

Сейчас карточка букета открывается как модальное окно поверх фоновой страницы через
`location.state.backgroundLocation`.

Сценарии:

- с главной, каталога, промо и избранного пользователь переходит на URL букета;
- приложение сохраняет фон в `backgroundLocation`;
- поверх фона рендерится `BouquetModal`;
- прямой заход на `/bouquet/:bouquetId` тоже должен показать букет.

Риск: модальная логика в `App.tsx`, страницах каталога/промо/избранного и `BouquetModal`
распределена по нескольким местам. Перед переносом на Next.js ее нужно отдельно описать
и упростить.

## Текущие API-запросы

Основной backend:

```text
https://api-v2.myata-flowers.ru
```

Каталог букетов:

```text
GET https://api-v2.myata-flowers.ru/api/bouquets
GET https://api-v2.myata-flowers.ru/api/bouquets?categories=<category>
GET https://api-v2.myata-flowers.ru/api/bouquets?showHidden=true
POST https://api-v2.myata-flowers.ru/api/bouquets
PUT https://api-v2.myata-flowers.ru/api/bouquets/:id
DELETE https://api-v2.myata-flowers.ru/api/bouquets/:id
POST https://api-v2.myata-flowers.ru/api/bouquets/upload
```

Админ-авторизация:

```text
POST https://api-v2.myata-flowers.ru/admin/login
```

Отправка заявки:

```text
POST /api/telegram/send
```

Важно: часть endpoint-ов захардкожена в коде. Перед Next.js POC и перед разделением
окружений нужно вынести API base URL в env/config и собрать единый API слой.

Текущий основной тип `IBouquet`:

- `oldPrice`;

Что сейчас не хватает для будущих SEO/посадочных:

- canonical URL;
- alt/title для изображений;
- структурированные поля под поводы;
- связи с посадочными страницами;
- приоритет/сортировка;
- дата обновления для sitemap.

## Категории и подборки

Есть конфиги:

- `src/shared/categories/config/bouquetCategories.ts`;
- `src/shared/categories/config/specialOffersCategories.ts`.

На главной категории также заданы локальным массивом в `MainPage`.

Риск: категории частично живут в коде, частично в данных backend. Это усложняет SEO,
фильтрацию, посадочные страницы и CMS. Нужно привести категории к единой модели.

## Главная страница

Главная сейчас включает:

- карусель популярного;
- CTA на подбор букета;
- блоки категорий;
- описание продукта/магазина;
- доставку и оформление;
- отзывы;
- финальный CTA.

Техническая особенность: главная делает несколько отдельных запросов по категориям.
Это работает, но может давать лишнюю сетевую нагрузку и сложнее переносится в SSR/SSG.

## Каталог

Каталог показывает:

- все букеты, если категория не выбрана;
- букеты выбранной категории;
- сортировку по цене;
- модальное открытие букета;
- переход из короткого блока главной в полный каталог категории.

Сейчас категория в URL передается как человекочитаемый текст. Для SEO лучше перейти
к стабильным slug, сохранив совместимость или редиректы.

## Избранное

Избранное хранит id букетов в `localStorage`.

Сценарии:

- добавить/убрать букет из карточки;
- открыть страницу `/favorites`;
- открыть букет из избранного;
- если избранное пустое, показать CTA на заявку.

Для SSR/Next это останется client-only функцией.

## Форма заявки

Форма использует Redux state и отправляет данные в `/api/telegram/send`.

Поля заявки:

- имя;
- телефон;
- букет;
- предпочтительный способ связи: call, telegram, whatsapp, max;
- дополнительные вопросы;
- honeypot против простых ботов;
- согласие на обработку персональных данных.

После отправки:

- отправляются цели Метрики;
- данные уходят в Telegram endpoint;
- показывается success message.

Риск: `sendToTelegram` логирует ошибку, но пользовательский сценарий ошибки отправки
нужно дополнительно проверить и улучшить.

## Админка

Ручная админка живет в `src/pages/admin/*`.

Функции:

- вход через `/admin`;
- хранение token в `localStorage`;
- создание букета;
- редактирование букета;
- удаление букета;
- переключение доступности;
- скрытие букета;
- загрузка изображений;
- просмотр таблицы букетов.

Риски:

- админка уже разрастается;
- часть URL захардкожена;
- форма большая;
- есть старые закомментированные блоки;
- нет отдельного API client;
- нет ролей/черновиков/истории изменений;
- при переходе на CMS нужно решить, переносить каталог сразу или оставить гибрид.

## SEO сейчас

Что есть:

- базовые meta в `index.html`;
- `robots.txt`;
- статический `sitemap.xml`;
- публичные URL категорий и букетов.

Ограничения:

- приложение рендерится как SPA;
- metadata общие, а не на каждую страницу;
- страницы букетов и категорий не имеют полноценного SSR/SSG контента;
- sitemap статический и требует процесса обновления;
- нет посадочных страниц под поводы, корпоративных клиентов, подписку и рекламу.

## Текущие проблемы и риски

- Проект сейчас в большом форматирующем diff после первого Prettier baseline.
- `README.md`, `FRONTEND_SERVER_GUIDE.md`, `SERVER_TUTORIAL.md`,
  `ARCHITECT_AGENT_PROMPT.md` пока не закоммичены.
- API endpoint-ы захардкожены.
- Модальная навигация сложная и распределена по нескольким файлам.
- Главная делает несколько запросов по категориям.
- Категории не имеют стабильной slug-модели.
- SEO ограничено SPA-архитектурой.
- Sitemap статический.
- Нет отдельного слоя контента для акций, посадочных, подписок, корпоративных блоков.
- Админка ручная и требует решения: улучшать ее, переносить в CMS или делать гибрид.
- Нужно отдельно проверить dependency audit, когда будет стабильная сеть.
